## گزارش پیاده‌سازی و استفاده از Git

در فرآیند توسعه این نرم‌افزار، از متدولوژی استاندارد Git Flow الهام گرفته شده است. تمام دستورات به صورت دستی در ترمینال اجرا شده‌اند تا تسلط بر مکانیزم‌های گیت تضمین گردد.

### ۱. استراتژی شاخه‌ها (Branches)
برای مدیریت بهینه، از حداقل ۳ شاخه معنا‌دار استفاده شده است:
*   **`main`**: شاخه اصلی و پایدار پروژه. این شاخه در گیت‌هاب **محافظت شده (Protected)** است و ادغام کدها تنها از طریق Pull Request امکان‌پذیر است.
*   **`development`**: شاخه توسعه فعال. تمام ویژگی‌های جدید پس از تکمیل به این شاخه ادغام می‌شوند.
*   **`feature/file-system`** (و سایر feature ها): شاخه‌های موقت برای توسعه یک قابلیت خاص (مانند ساخت سیستم‌فایل و اکسپلورر) که از `development` منشعب شده و پس از تکمیل با آن ادغام می‌گردند.

### ۲. استراتژی ثبت تغییرات (Commits)
تلاش شده است تا کامیت‌ها به صورت **Atomic** (انجام تنها یک کار مشخص در هر کامیت) و با پیام‌های معنادار (Semantic Commit Messages) ثبت شوند (بیش از ۲۰ کامیت در طول توسعه). مثال: `feat: build file explorer and dynamic context menus` یا `style: update compiled tailwind css`.

### ۳. مدیریت تداخل‌ها (Conflicts)
[توضیحات مربوط به ۲ کانفلیکت ایجاد شده و نحوه حل آن‌ها در مراحل بعدی توسعه در اینجا نوشته خواهد شد.]

### ۴. استقرار خودکار (CI/CD)
با استفاده از قابلیت GitHub Actions، یک Workflow تنظیم شده است که با هر بار Push شدن تغییرات نهایی در شاخه `main`، پروژه به صورت خودکار بیلد شده و روی GitHub Pages مستقر (Deploy) می‌گردد.

## پاسخ به پرسش‌ها

### ۱. پوشه‌ی `git.` چیست؟
پوشه مخفی `.git` قلب تپنده و پایگاه داده محلی گیت در پروژه است. این پوشه با دستور `git init` ساخته می‌شود. تمامی اطلاعات مربوط به تاریخچه تغییرات، کامیت‌ها، شاخه‌ها (Branches)، تگ‌ها و تنظیمات پروژه در این پوشه ذخیره می‌شود. اگر این پوشه پاک شود، پروژه شما به یک پوشه معمولی تبدیل شده و تمام تاریخچه گیت از بین می‌رود.

### ۲. منظور از atomic بودن در atomic commit و atomic pull-request چیست؟
مفهوم **Atomic** (اتمی یا تجزیه‌ناپذیر) یعنی هر کامیت یا PR باید **تنها و تنها یک تغییر منطقی و مشخص** را در بر بگیرد. مثلاً نباید در یک کامیت، هم یک باگ را رفع کرد و هم یک ویژگی جدید اضافه کرد. 
مزیت این کار: درک آسان‌تر تاریخچه، راحت‌تر بودن بررسی کد (Code Review) در PR، و قابلیت بازگردانی (Revert) یک ویژگی بدون آسیب زدن به سایر بخش‌های کد است.

### ۳. تفاوت دستورهای fetch, pull, merge, rebase, cherry-pick
*   `fetch`: اطلاعات و تغییرات جدید را از مخزن ریموت (مثل گیت‌هاب) دانلود می‌کند اما آن‌ها را با فایل‌های فعلی شما ادغام نمی‌کند (فقط برای مشاهده تغییرات).
*   `pull`: ترکیب دو دستور `fetch` و `merge` است. یعنی تغییرات را دانلود کرده و بلافاصله با شاخه فعلی شما ادغام می‌کند.
*   `merge`: تاریخچه دو شاخه را با هم ترکیب کرده و یک کامیت جدید (Merge Commit) می‌سازد تا نشان دهد این دو مسیر به هم پیوسته‌اند.
*   `rebase`: به جای ترکیب، شاخه فعلی را برداشته و دقیقاً روی "نوک" (آخرین کامیت) شاخه هدف قرار می‌دهد. این کار تاریخچه را خطی و تمیز می‌کند (اما نباید روی شاخه‌های عمومی استفاده شود).
*   `cherry-pick`: یک کامیت خاص را از یک شاخه دیگر انتخاب کرده و کپی آن را در شاخه فعلی شما اعمال می‌کند.

### ۴. تفاوت دستورهای reset, revert, restore, switch, checkout
*   `reset`: نشانگر (HEAD) را به یک کامیت قدیمی‌تر برمی‌گرداند و تاریخچه بعد از آن را پاک می‌کند. (می‌تواند تغییرات فایل‌ها را نیز با سوئیچ `--hard` پاک کند).
*   `revert`: تاریخچه را پاک نمی‌کند، بلکه یک کامیت جدید می‌سازد که تغییرات کامیت قبلی را خنثی (Undo) می‌کند. امن‌ترین راه برای لغو تغییرات در تیم است.
*   `restore`: برای بازگرداندن فایل‌های تغییر یافته به حالت قبلی (خارج کردن از حالت stage یا حذف تغییرات ذخیره نشده) استفاده می‌شود.
*   `switch`: دستور جدیدی است که مشخصاً و فقط برای تغییر دادن شاخه فعلی (جابجایی بین branch ها) استفاده می‌شود.
*   `checkout`: دستور قدیمی گیت که دو کار کاملاً متفاوت انجام می‌داد (هم تغییر شاخه و هم بازگردانی فایل‌ها). به همین دلیل در نسخه‌های جدید گیت، به دو دستور `switch` و `restore` تفکیک شد.

### ۵. منظور از stage (index) چیست؟ دستور stash چه کاری انجام می‌دهد؟
*   **Stage (Index):** ناحیه آماده‌سازی یا اتاق انتظار گیت است. شما فایل‌های تغییر یافته را با `git add` وارد این ناحیه می‌کنید تا به گیت بگویید: "این تغییرات برای کامیت بعدی آماده هستند."
*   **Stash:** زمانی که در حال کار روی چیزی هستید اما مجبورید سریعاً شاخه را عوض کنید (ولی کارتان تمام نشده که کامیت کنید)، با دستور `git stash` تغییرات فعلی را در یک حافظه موقت می‌ریزید تا پوشه کاری شما تمیز شود. بعداً می‌توانید با `git stash pop` آن‌ها را برگردانید.

### ۶. مفهوم snapshot چیست و ارتباط آن با commit چیست؟
گیت برخلاف سیستم‌های قدیمی که فقط تفاوت فایل‌ها (Delta) را ذخیره می‌کردند، مانند یک دوربین عکاسی عمل می‌کند. **Snapshot** یعنی یک عکس کامل از وضعیت تمام فایل‌های پروژه در یک لحظه مشخص. 
هر **Commit** در واقع یک Snapshot است که اطلاعات اضافه‌ای مانند نام نویسنده، تاریخ، پیام کامیت و اشاره‌گر به کامیت قبلی (Parent) به آن چسبیده است.

### ۷. تفاوت local repository و remote repository
*   **Local Repository:** مخزنی است که روی کامپیوتر شخصی شما (درون همان پوشه `.git`) قرار دارد. شما می‌توانید به صورت آفلاین کامیت کنید، شاخه بسازید و تاریخچه را مدیریت کنید.
*   **Remote Repository:** مخزنی است که روی یک سرور اینترنتی (مثل GitHub یا GitLab) قرار دارد. برنامه‌نویسان برای همگام‌سازی کار تیمی، کدهای Local خود را به سرور Remote پوش (Push) کرده یا از آن پول (Pull) می‌کنند.
