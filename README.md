## گزارش پیاده‌سازی و گردش‌کار Git

برای انجام این آزمایش و پیاده‌سازی پروژه، سعی کردم تماماً از محیط خط فرمان (CLI) استفاده کنم تا درک بهتری از مکانیزم‌های گیت پیدا کنم. گردش‌کار (Workflow) استفاده شده الهام گرفته از Git Flow است.

### ۱. مدیریت شاخه‌ها (Branching)
پروژه به صورت تک‌شاخه‌ای پیش نرفته و از ساختار زیر استفاده کردم:
*   **`main`**: شاخه اصلی و نهایی. برای رعایت اصول کار تیمی، این شاخه در تنظیمات گیت‌هاب **Protect** شده است؛ به این معنی که هیچ‌کس نمی‌تواند مستقیماً روی آن Push کند و تغییرات فقط از طریق باز کردن Pull Request و تایید آن اعمال می‌شود.
*   **`development`**: شاخه‌ی توسعه. تمام کارهای اصلی ابتدا در این شاخه تایید و سپس به `main` منتقل می‌شوند.
*   **شاخه‌های ویژگی (Feature Branches)**: برای توسعه هر بخش (مثلاً `feature/file-system`) شاخه جدیدی از دولوپمنت ایجاد کردم و پس از اتمام کار، آن را در دولوپمنت ادغام (Merge) کردم.

### ۲. ثبت تغییرات (Commits)
سعی کردم مفهوم **Atomic Commit** را رعایت کنم؛ یعنی هر کامیت فقط شامل یک تغییر منطقی مشخص باشد (بیش از ۲۰ کامیت معنادار). همچنین برای نام‌گذاری کامیت‌ها از استاندارد Semantic (مثل `feat:`, `fix:`, `style:`) استفاده کردم تا تاریخچه پروژه خوانا باشد.

### ۳. تداخل‌ها (Conflicts)
[توضیح: در فرآیند توسعه، دو تداخل (Conflict) عمدی/سهوی ایجاد شد که یکی در زمان ادغام شاخه‌ها و دیگری در زمان تغییر همزمان یک فایل بود. این تداخل‌ها به صورت دستی در ویرایشگر بررسی و با انتخاب کدهای صحیح (Resolve) برطرف شدند.] *(نکته برای علی: این بخش را پس از انجام مرحله کانفلیکت با هم تکمیل می‌کنیم).*

### ۴. استقرار مستمر (CI/CD)
برای استقرار خودکار، از GitHub Actions استفاده کردم. یک فایل Workflow (`deploy.yml`) تنظیم شد که به محض مرج شدن تغییرات در شاخه `main`، کدهای استاتیک را دریافت کرده و به طور خودکار روی GitHub Pages بارگذاری می‌کند.

## موارد استفاده از هوش مصنوعی (AI)
در روند توسعه این پروژه، به عنوان یک برنامه‌نویس از مدل‌های زبانی هوش مصنوعی (LLM) به عنوان دستیار (Pair Programmer) استفاده کردم. موارد اصلی استفاده عبارتند از:
1. **تولید اسکلت اولیه (Boilerplate):** برای سرعت بخشیدن به کار، ساختار اولیه کلاس‌های جاوااسکریپت (مفاهیم شی‌گرایی) و قالب‌بندی پایه HTML/Tailwind توسط هوش مصنوعی ایجاد شد و سپس منطق اصلی روی آن‌ها پیاده‌سازی گردید.
2. **پیکربندی استقرار (Deployment):** برای نوشتن فایل `deploy.yml` در بخش GitHub Actions از هوش مصنوعی کمک گرفتم تا نیازی به درگیر شدن با خطاهای سینتکسی YAML نباشد.
3. **نگارش و قالب‌بندی مستندات:** برای مرتب‌سازی فایل README و ایجاد ساختار استاندارد Markdown برای پاسخ به پرسش‌ها از هوش مصنوعی استفاده شد.

## پاسخ به پرسش‌های آزمایش

### ۱. پوشه‌ی `git.` چیست؟
این پوشه‌ی پنهان، پایگاه داده محلی گیت است که با دستور `git init` ساخته می‌شود. گیت تمام تاریخچه تغییرات، مشخصات کامیت‌ها، تنظیمات پروژه و اطلاعات شاخه‌ها را در این پوشه ذخیره می‌کند.

### ۲. منظور از atomic بودن در کامیت و PR چیست؟
اتمی بودن یعنی هر کامیت یا Pull Request **فقط و فقط یک تغییر یا ویژگی خاص** را شامل شود (تجزیه‌ناپذیر باشد). مثلاً نباید در یک کامیت، هم ظاهر دکمه را عوض کرد و هم منطق دیتابیس را تغییر داد. این کار باعث می‌شود پیدا کردن باگ‌ها و یا برگرداندن کد (Revert) به شدت آسان شود.

### ۳. تفاوت دستورهای fetch, pull, merge, rebase, cherry-pick
*   `fetch`: فقط اطلاعات جدید را از سرور دانلود می‌کند تا ببینیم چه تغییراتی رخ داده، اما روی کدهای فعلی ما اعمالشان نمی‌کند.
*   `pull`: کار fetch را انجام می‌دهد و بلافاصله کدهای جدید را با کدهای سیستم ما ادغام (merge) می‌کند.
*   `merge`: تاریخچه دو شاخه را با هم ترکیب می‌کند و یک کامیت جدید برای اتصال آن‌ها می‌سازد.
*   `rebase`: به جای ساخت کامیت جدید، شاخه ما را از ریشه جدا کرده و دقیقاً در انتهای شاخه مقصد قرار می‌دهد تا تاریخچه به صورت یک خط صاف و تمیز دربیاید.
*   `cherry-pick`: فقط یک کامیت خاص (با شناسه مشخص) را از شاخه‌ای دیگر کپی کرده و روی شاخه فعلی اعمال می‌کند.

### ۴. تفاوت دستورهای reset, revert, restore, switch, checkout
*   `reset`: زمان را به عقب برمی‌گرداند و تاریخچه کامیت‌های بعد از خود را پاک می‌کند (مخرب است).
*   `revert`: تاریخچه را پاک نمی‌کند، بلکه یک کامیت جدید می‌سازد که اثرات کامیت قبلی را خنثی می‌کند (روش ایمن).
*   `restore`: فایل‌های تغییریافته و ذخیره‌نشده را به حالت قبلی برمی‌گرداند یا از حالت Stage خارج می‌کند.
*   `switch`: مشخصاً برای جابجایی بین شاخه‌ها (Branches) استفاده می‌شود.
*   `checkout`: دستور قدیمی گیت که هم برای تغییر شاخه و هم برای برگرداندن فایل‌ها استفاده می‌شد (اکنون به switch و restore تفکیک شده است).

### ۵. منظور از stage (index) و stash چیست؟
*   **Stage (Index):** یک "اتاق انتظار" است. فایل‌هایی که تغییر داده‌ایم را با دستور `git add` به این ناحیه می‌فرستیم تا مشخص کنیم دقیقاً کدام تغییرات باید در کامیت بعدی ثبت شوند.
*   **Stash:** یک "حافظه موقت" است. وقتی کدمان نصفه‌کاره است اما مجبوریم سریعاً شاخه را عوض کنیم، با دستور `git stash` تغییرات را موقتاً در یک کلیپ‌بورد ذخیره می‌کنیم تا بعداً دوباره آن‌ها را فراخوانی کنیم.

### ۶. مفهوم snapshot و ارتباط آن با commit
گیت بر خلاف سیستم‌های قدیمی، تفاوت خطوط (Delta) را ذخیره نمی‌کند. گیت در هر بار ثبت تغییرات، مانند یک دوربین از کل ساختار فایل‌ها یک عکس (Snapshot) می‌گیرد. هر کامیت در واقع اشاره‌گری به یکی از همین Snapshot هاست.

### ۷. تفاوت local repository و remote repository
*   **Local:** مخزنی است که روی کامپیوتر شخصی ما قرار دارد. تمام عملیات‌ها مثل کامیت و ساخت شاخه در اینجا به صورت آفلاین انجام می‌شود.
*   **Remote:** مخزنی است که روی یک سرور اینترنتی (مثل GitHub) میزبانی می‌شود تا اعضای تیم کدهای Local خود را با آن همگام‌سازی (Push و Pull) کنند.
