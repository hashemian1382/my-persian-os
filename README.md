## گزارش پیاده‌سازی و گردش‌کار Git

برای انجام این آزمایش و پیاده‌سازی پروژه، سعی کردم تماماً از محیط خط فرمان (CLI) استفاده کنم تا درک بهتری از مکانیزم‌های گیت پیدا کنم. گردش‌کار (Workflow) استفاده شده، با الهام از متدولوژی Git Flow طراحی شده است.

### ۱. مدیریت شاخه‌ها (Branching)
پروژه به صورت تک‌شاخه‌ای پیش نرفته و از ساختار زیر استفاده کردم:
*   **`main`**: شاخه اصلی و نهایی. برای رعایت اصول کار تیمی، این شاخه در تنظیمات گیت‌هاب **Protect** شده است؛ به این معنی که هیچ‌کس نمی‌تواند مستقیماً روی آن Push کند و تغییرات فقط از طریق باز کردن Pull Request و تایید آن اعمال می‌شود.
*   **`development`**: شاخه‌ی توسعه. تمام ویژگی‌های جدید ابتدا در این شاخه تایید و تجمیع شده و سپس به `main` منتقل می‌شوند.
*   **شاخه‌های ویژگی (Feature Branches)**: برای توسعه هر بخش مجزا (مانند `feature/file-system` یا `feature/desktop-gui`)، شاخه جدیدی از دولوپمنت ایجاد کردم و پس از اتمام کار، آن را در دولوپمنت ادغام (Merge) کردم.

### ۲. ثبت تغییرات (Commits)
تلاش کردم مفهوم **Atomic Commit** را رعایت کنم؛ یعنی هر کامیت فقط شامل یک تغییر منطقی و مشخص باشد (در این پروژه بیش از ۲۰ کامیت معنادار ثبت شده است). همچنین برای نام‌گذاری کامیت‌ها از استاندارد Semantic (مثل `feat:`, `fix:`, `style:`) استفاده کردم تا تاریخچه پروژه خوانا و حرفه‌ای باشد.

### ۳. مدیریت تداخل‌ها (Conflicts)
برای تسلط بر نحوه رفع تداخل در گیت، طبق خواسته آزمایش، دو سناریوی مختلف را به صورت دستی ایجاد و حل کردم:

*   **تداخل اول (هنگام ادغام دو شاخه):**
    برای شبیه‌سازی این حالت، یک شاخه جدید به نام `feature/update-docs` ساختم و خط چهارم همین فایل `README.md` را ویرایش کردم (عبارت "وضعیت پروژه" را نوشتم). سپس به شاخه `development` برگشتم و دقیقاً در همان خط، متن متفاوتی ("نسخه پروژه") را اضافه و کامیت کردم. 
    وقتی دستور `git merge feature/update-docs` را زدم، گیت به دلیل تغییرات متضاد در یک خط یکسان، اخطار Conflict داد و متوقف شد. برای رفع آن، فایل را در ادیتور باز کردم، نشانگرهای گیت (`<<<<` و `====`) را دستی پاک کردم، تصمیم گرفتم هر دو خط را زیر هم نگه دارم و در نهایت فایل را مجدداً Add و Commit کردم تا ادغام با موفقیت تکمیل شود.

*   **تداخل دوم (هنگام دریافت کدهای سرور در یک شاخه):**
    این سناریو برای شبیه‌سازی تداخل در کار تیمی انجام شد. ابتدا مستقیماً روی سایت گیت‌هاب (Remote) در شاخه `development`، رنگ اسکرول‌بار را در فایل `style.css` به قرمز تغییر دادم و کامیت کردم. سپس در سیستم خودم (Local)، بدون دریافت کدهای سرور، همان خط از فایل CSS را باز کرده و رنگ را به آبی تغییر دادم و کامیت زدم. 
    با اجرای دستور `git pull origin development` برای دریافت تغییرات هم‌تیمی (سرور)، تداخل رخ داد. فایل CSS را باز کردم، تصمیم گرفتم رنگ آبی (کد لوکال خودم) را نگه دارم، پس کدهای مربوط به سرور را پاک کردم و با یک کامیت جدید، تداخل را حل کرده و نتیجه نهایی را به سرور Push کردم.

### ۴. استقرار مستمر (CI/CD)
برای استقرار خودکار، از قابلیت GitHub Actions استفاده کردم. یک فایل Workflow به نام `deploy.yml` تنظیم شد که به محض مرج شدن تغییرات در شاخه `main`، کدهای استاتیک را دریافت کرده و بدون نیاز به دخالت دستی، به طور خودکار روی GitHub Pages بارگذاری (Deploy) می‌کند.

## موارد استفاده از هوش مصنوعی (AI)
در روند توسعه این پروژه، به عنوان یک برنامه‌نویس از مدل‌های زبانی هوش مصنوعی (LLM) به عنوان دستیار (Pair Programmer) استفاده کردم. موارد اصلی استفاده عبارتند از:
1. **تولید اسکلت اولیه (Boilerplate):** برای سرعت بخشیدن به کار، ساختار اولیه کلاس‌های جاوااسکریپت و قالب‌بندی پایه HTML/Tailwind توسط هوش مصنوعی ایجاد شد و سپس منطق اصلی و اتصال فایل‌سیستم روی آن‌ها پیاده‌سازی گردید.
2. **پیکربندی استقرار (Deployment):** برای نوشتن فایل `deploy.yml` در بخش GitHub Actions از هوش مصنوعی کمک گرفتم تا نیازی به درگیر شدن با خطاهای سینتکسی YAML و اکشن‌های آماده گیت‌هاب نباشد.
3. **نگارش و قالب‌بندی مستندات:** برای مرتب‌سازی نهایی فایل README و ایجاد ساختار استاندارد Markdown برای پاسخ به پرسش‌ها از هوش مصنوعی استفاده شد.

## پاسخ به پرسش‌های آزمایش

### ۱. پوشه‌ی `git.` چیست؟
این پوشه‌ی پنهان، در واقع پایگاه داده و قلب تپنده محلی گیت است که با دستور `git init` ساخته می‌شود. گیت تمام تاریخچه تغییرات، مشخصات کامیت‌ها، تنظیمات پروژه و اطلاعات شاخه‌ها را در این پوشه ذخیره می‌کند. اگر این پوشه پاک شود، پروژه به یک پوشه معمولی تبدیل شده و تمام تاریخچه گیت از بین می‌رود.

### ۲. منظور از atomic بودن در کامیت و PR چیست؟
اتمی بودن یعنی هر کامیت یا Pull Request **فقط و فقط یک تغییر یا ویژگی خاص** را شامل شود (تجزیه‌ناپذیر باشد). مثلاً نباید در یک کامیت، هم ظاهر یک دکمه را عوض کرد و هم منطق دیتابیس را تغییر داد. این کار باعث می‌شود پیدا کردن باگ‌ها، بررسی کدها (Code Review) و یا برگرداندن کد (Revert) به شدت آسان شود.

### ۳. تفاوت دستورهای fetch, pull, merge, rebase, cherry-pick
*   **`fetch`**: فقط اطلاعات جدید را از سرور دانلود می‌کند تا ببینیم چه تغییراتی رخ داده، اما آن‌ها را روی کدهای فعلی ما اعمال (ادغام) نمی‌کند.
*   **`pull`**: ترکیب دو دستور `fetch` و `merge` است. یعنی تغییرات را دانلود کرده و بلافاصله با کدهای سیستم ما ادغام می‌کند.
*   **`merge`**: تاریخچه دو شاخه را با هم ترکیب می‌کند و یک کامیت جدید (Merge Commit) برای اتصال آن‌ها می‌سازد.
*   **`rebase`**: به جای ساخت کامیت جدید، شاخه ما را از ریشه جدا کرده و دقیقاً در انتهای شاخه مقصد قرار می‌دهد تا تاریخچه به صورت یک خط صاف و تمیز دربیاید.
*   **`cherry-pick`**: فقط یک کامیت خاص (با شناسه مشخص) را از شاخه‌ای دیگر کپی کرده و روی شاخه فعلی اعمال می‌کند.

### ۴. تفاوت دستورهای reset, revert, restore, switch, checkout
*   **`reset`**: زمان را به عقب برمی‌گرداند و تاریخچه کامیت‌های بعد از خود را پاک می‌کند (دستوری مخرب است و نباید روی کدهای به اشتراک گذاشته شده استفاده شود).
*   **`revert`**: تاریخچه را پاک نمی‌کند، بلکه یک کامیت جدید می‌سازد که اثرات کامیت قبلی را خنثی (Undo) می‌کند (روشی کاملاً ایمن برای تیم).
*   **`restore`**: فایل‌های تغییریافته و ذخیره‌نشده را به حالت قبلی برمی‌گرداند یا آن‌ها را از حالت Stage خارج می‌کند.
*   **`switch`**: دستوری جدید که مشخصاً فقط برای جابجایی بین شاخه‌ها (Branches) استفاده می‌شود.
*   **`checkout`**: دستور قدیمی گیت که هم برای تغییر شاخه و هم برای برگرداندن فایل‌ها استفاده می‌شد (اکنون برای جلوگیری از سردرگمی به `switch` و `restore` تفکیک شده است).

### ۵. منظور از stage (index) و stash چیست؟
*   **Stage (Index):** یک "اتاق انتظار" است. فایل‌هایی که تغییر داده‌ایم را با دستور `git add` به این ناحیه می‌فرستیم تا به گیت بگوییم دقیقاً کدام تغییرات باید در کامیت بعدی ثبت شوند.
*   **Stash:** یک "حافظه موقت" است. وقتی کدمان نصفه‌کاره است اما مجبوریم سریعاً شاخه را عوض کنیم، با دستور `git stash` تغییرات را موقتاً در یک کلیپ‌بورد ذخیره می‌کنیم تا پوشه کاری تمیز شود. بعداً می‌توانیم با `git stash pop` آن‌ها را دوباره فراخوانی کنیم.

### ۶. مفهوم snapshot و ارتباط آن با commit
گیت بر خلاف سیستم‌های قدیمی، تفاوت خطوط فایل‌ها (Delta) را ذخیره نمی‌کند. گیت در هر بار ثبت تغییرات، مانند یک دوربین عکاسی از کل ساختار فایل‌ها یک عکس (Snapshot) می‌گیرد. هر **Commit** در واقع اشاره‌گری به یکی از همین Snapshot هاست که اطلاعات اضافه‌ای مانند نام نویسنده، تاریخ و پیام کامیت به آن پیوست شده است.

### ۷. تفاوت local repository و remote repository
*   **Local Repository:** مخزنی است که روی کامپیوتر شخصی برنامه‌نویس قرار دارد. تمام عملیات‌ها مثل کامیت و ساخت شاخه در اینجا به صورت آفلاین و مستقل انجام می‌شود.
*   **Remote Repository:** مخزنی است که روی یک سرور اینترنتی (مثل GitHub یا GitLab) میزبانی می‌شود تا اعضای تیم بتوانند کدهای Local خود را با آن همگام‌سازی (Push و Pull) کرده و با یکدیگر همکاری کنند.
